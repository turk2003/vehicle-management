# บทซ้อม Demo อธิบายโค้ด และตอบกรรมการ

สำหรับสอบโครงงาน 2 วันที่ 8 พฤศจิกายน 2569 อ่านคู่กับ [แผนรายวันและโครงสไลด์](08-exam-preparation-plan.md) โค้ดและตำแหน่งบรรทัดตรวจวันที่ 31 ตุลาคม 2569 หากแก้ source ให้ค้นจากชื่อฟังก์ชันอีกครั้ง

## 1. บทเปิดประมาณ 45–60 วินาที

> สวัสดีครับ ผมนำเสนอโครงงานระบบจัดการยานพาหนะภายในองค์กรครับ ระบบครอบคลุมการขอใช้รถ การอนุมัติ การรับและคืนรถ งานซ่อมบำรุง และรายงานการใช้งาน โดยแบ่งผู้ใช้เป็นผู้ขอใช้ ผู้อนุมัติ และผู้ดูแลระบบ
>
> จุดสำคัญของโครงการคือเชื่อมข้อมูลตั้งแต่คำขอไปจนถึงหลักฐานการใช้รถจริง เช่นเวลารับคืนและเลขไมล์ ตัวเว็บใช้ Next.js และ React ส่วน API ตรวจสิทธิ์กับเงื่อนไขการทำรายการ ก่อนใช้ Prisma ติดต่อ PostgreSQL ครับ
>
> รายงานคำนวณตัวเลขจากข้อมูลต้นทาง และมี AI ช่วยสรุปข้อมูลสำหรับผู้ดูแล วันนี้ผมจะอธิบายตามเนื้อหา 5 บท พร้อมยกโค้ดสำคัญที่ทำให้ระบบทำงานตามเงื่อนไขครับ

ชื่อโครงการและวัตถุประสงค์ควรปรับให้ตรงกับเล่มจริง ไม่จำเป็นต้องท่องถ้อยคำตามนี้ทุกคำ ให้จำลำดับ “ทำอะไร ใครใช้ ทำงานอย่างไร และจุดสำคัญคืออะไร”

## 2. บทเชื่อมระหว่าง 5 บท

| ช่วง | ประโยคเริ่มที่ใช้ซ้อม | สิ่งที่ต้องเสริมจากเล่ม |
|---|---|---|
| บท 1 | “โจทย์หลักคือการตรวจรถว่าง การพิจารณาคำขอ และการติดตามประวัติการใช้งานครับ” | ที่มาปัญหาและวัตถุประสงค์ตามเล่ม รวมหลักฐานการสำรวจถ้ามี |
| บท 2 | “หลักการที่นำมาใช้คือการแยกหน้าจอออกจากจุดตรวจข้อมูลบน server การจัดความสัมพันธ์ข้อมูล และการกำหนดสิทธิ์ตามบทบาทครับ” | งานที่เกี่ยวข้องและเอกสารอ้างอิงที่อ่านจริง |
| บท 3 | “เมื่อผู้ใช้ส่งฟอร์ม ข้อมูลจะเข้า API เพื่อตรวจตัวตน สิทธิ์ และเงื่อนไข ก่อนสร้างรายการครับ ผมขอยกตัวอย่างจากการจองหนึ่งรายการ” | กระบวนการพัฒนาที่ทำจริง และแบบออกแบบที่ตรงกับโค้ด |
| บท 4 | “ผลที่แสดงส่วนนี้คือหน้าจอและข้อมูลที่ได้จากการทำรายการ รวมถึงผลทดสอบที่ระบุวันที่ครับ” | ภาพจริง ตารางทดสอบ และผลประเมินผู้ใช้ถ้ามี |
| บท 5 | “ผลที่ได้ตอบวัตถุประสงค์เรื่อง...ตามหลักฐานที่แสดง ส่วนข้อจำกัดที่ยังเหลือคือ...” | สรุปตามวัตถุประสงค์จริงและงานพัฒนาต่อ |

## 3. ชุดข้อมูลและขั้นตอน Demo จริง

กำหนดเวลาซ้อม Demo ประมาณ 6–8 นาทีเป็นข้อเสนอ ไม่ใช่เวลาที่ประกาศระบุ ใช้ฐานข้อมูลเดโมและข้อมูลสมมติที่เตรียมไว้ ไม่ต้องสร้างข้อมูลใหม่ลงฐานข้อมูลใช้งานจริงเพื่อซ้อม

### เตรียมก่อนเริ่ม

- มีบัญชี USER, APPROVER และ ADMIN ที่ login ได้จริงและมี Permission ตามงานที่จะทำ
- หากเปิดพร้อมกัน ให้ใช้ browser profile ที่แยกกัน หรือคนละ browser เพราะแท็บใน profile เดียวกันแชร์ cookie การเปิดสามแท็บอย่างเดียวไม่ได้แยกบัญชี
- มีรถเดโม A และ B ที่พร้อมใช้ ไม่มีการจอง/ซ่อมทับช่วงที่เลือก
- รู้เลขไมล์ปัจจุบันของรถก่อนกรอก ห้ามยึดเลขไมล์สมมติหากไม่ตรงข้อมูลเดโม
- ใช้ชื่อรายการที่ค้นพบง่าย เช่น “DEMO สอบโครงงาน2 รอบ1” และเพิ่มรอบเมื่อซ้อมใหม่
- เตรียมรายการ PENDING, APPROVED และ COMPLETED คนละรายการไว้สำรอง เผื่อจุดหนึ่งสะดุด
- ช่วงเวลาจองต้องอยู่ในอนาคตขณะสร้างคำขอ และวันรายงานต้องครอบคลุมเวลาคืนรถจริง
- ตรวจเงื่อนไขเวลา/สถานะในเครื่องก่อนสอบ อย่าแก้นาฬิกาเครื่องหรือแก้ฐานข้อมูลขณะนำเสนอเพื่อบังคับให้ flow ผ่าน

### ฉากหลัก: คำขอหนึ่งรายการจนเป็นรายงาน

| ลำดับ | บทบาท/หน้าจอ | การกระทำ | สิ่งที่ควรสังเกตและพูด |
|---|---|---|---|
| 1 | USER `/user/booking` | ค้นหารถในช่วงที่เตรียมไว้ เลือกรถ กรอกวัตถุประสงค์และปลายทาง | “ช่วงเวลานี้ระบบตรวจทั้งการจองและงานซ่อมก่อนแสดงตัวเลือกครับ” |
| 2 | USER `/user/my-bookings` | ส่งคำขอและเปิดรายการ | “รายการใหม่อยู่ในสถานะรออนุมัติ และผูกกับบัญชีผู้ส่งคำขอครับ” |
| 3 | APPROVER `/approver/approve` | เปิดรายการเดิมและอนุมัติ | “ผู้พิจารณามีสิทธิ์อนุมัติ และระบบบันทึกผู้พิจารณาไว้ครับ” |
| 4 | USER `/user/my-bookings` | รับรถ โดยกรอกเลขไมล์ไม่น้อยกว่าปัจจุบัน | “ระบบบันทึกเลขไมล์กับเวลารับจริง และเปลี่ยนรายการเป็นกำลังใช้งานครับ” |
| 5 | USER หน้ารายการเดิม | ลองเลขไมล์คืนต่ำกว่าเริ่มหนึ่งครั้ง จากนั้นคืนด้วยค่าที่ถูกต้อง | “ข้อมูลไม่ผ่านจะยังไม่ปิดเที่ยว เมื่อเลขไมล์ถูกต้องจึงบันทึกการคืนครับ” |
| 6 | ADMIN `/admin/vehicle-history` | เลือกรถและช่วงวันที่ครอบคลุมวันคืน | “รายงานนับเที่ยวที่เสร็จสิ้นแล้ว ระยะทางมาจากเลขไมล์ของแต่ละเที่ยวครับ” |
| 7 | ADMIN หน้าเดิม | สั่งบทสรุป AI หากตั้งค่าและบริการพร้อม | “AI อ่านตัวชี้วัดที่ระบบคำนวณแล้ว ผลนี้ใช้ประกอบการพิจารณาครับ” |

ถ้า frontend ป้องกันเลขไมล์ต่ำกว่าเริ่มตั้งแต่ฟอร์ม ให้แสดง validation ที่ผู้ใช้เห็นและอธิบายว่ามีการตรวจซ้ำที่ API ไม่จำเป็นต้องข้ามฟอร์มเพื่อบังคับให้เห็น HTTP error

ถ้ารับรถที่ M และคืนที่ M+120 ควรได้ระยะทาง 120 กม. เลือก M ตามเลขไมล์จริงของชุดข้อมูลเดโม การซ้อมแต่ละรอบทำให้เลขไมล์ปัจจุบันเปลี่ยน จึงต้องเตรียมรอบใหม่ให้สัมพันธ์กัน

### ฉากเสริม: รถเดิมไม่พร้อมก่อนรับรถ

1. เตรียมคำขออีกหนึ่งรายการที่อนุมัติแล้วและยังไม่รับรถ
2. แสดงการแจ้งซ่อมและการตรวจสอบของ Admin ด้วยข้อมูลเดโม
3. Admin เปิดตัวเลือกรถทดแทน เปลี่ยนรถพร้อมเหตุผลตามเงื่อนไขที่หน้าจออนุญาต
4. แสดงรายการใหม่ที่สัมพันธ์กับรถทดแทนและการแจ้งเตือน
5. อธิบายว่า CHANGED เป็นสถานะรายการ ส่วนสถานะรถคำนวณจากงานที่เกี่ยวข้อง

ฉากนี้ใช้เมื่อเวลาพอ หรือเก็บเป็นกรณีตอบคำถาม เตรียมไว้แยกจากรายการที่ใช้แสดงการรับคืนเสร็จแล้ว

### ถ้าบริการภายนอกไม่พร้อม

- เปิดรายงานตัวเลขจากระบบก่อน แยกสถานะของ AI ออกมาให้ชัด
- ถ้าแสดงผลที่บันทึกไว้ ให้บอกว่าเป็นผลจากรอบทดสอบก่อนหน้า พร้อมช่วงข้อมูลและวันที่
- อีเมลแสดงเป็นความสามารถที่ตั้งค่า SMTP แล้วทดสอบแยก การมี template หรือ mock test ไม่ยืนยันว่าอีเมลส่งถึงกล่องรับจริง
- วิดีโอและภาพเป็นหลักฐานสำรอง การใช้แทน Demo ต้องตามที่อาจารย์อนุญาต

## 4. รูปแบบการอธิบายโค้ด

ทุกจุดให้พูดตามลำดับ “โจทย์ → ข้อมูลเข้า → เงื่อนไขสำคัญ → ผลลัพธ์ → ข้อจำกัด” ใช้ประมาณ 45–75 วินาทีต่อจุด บนสไลด์เลือกเฉพาะโค้ดช่วงสั้น ส่วนโค้ดเต็มเปิดใน IDE เมื่อมีคำถาม

### จุด 1: การตรวจตัวตนและสิทธิ์

ต้นทาง: [booking POST](../../app/api/booking/route.ts) บรรทัด 115 และ [requireAccess](../../lib/permissions.ts) บรรทัด 68

```ts
const decoded = await requireAccess(req, {
  roles: ["USER"],
  permission: "BOOKING_CREATE",
})
```

```ts
const actor = await verifyToken(req)
return assertAccess(actor, policy)
```

บทพูด:

> ก่อนอ่านข้อมูลคำขอ ระบบตรวจว่าผู้เรียกยืนยันตัวตนแล้ว เป็น USER และมี BOOKING_CREATE ครับ requireAccess เรียก verifyToken แล้วตรวจ policy ต่อ โดย verifyToken อ่านบทบาทและสถานะบัญชีล่าสุดจาก DB ทำให้การปิดบัญชีหรือเปลี่ยนบทบาทมีผลกับ request ถัดไปได้ เมื่อผ่านจึงใช้ decoded.userId เป็นเจ้าของคำขอครับ

ต้องตอบต่อได้:

- Login ต่างจากมีสิทธิ์ทำรายการอย่างไร: ตัวตนกับขอบเขตงานเป็นคนละการตรวจ
- ซ่อนปุ่มเพียงพอไหม: API ยังต้องตรวจเพราะผู้เรียกส่ง HTTP เองได้
- ใช้ userId จาก body ได้ไหม: เจ้าของคำขอใหม่ใช้ค่าจากผู้ที่ยืนยันตัวตน
- Proxy ตรวจอะไร: ตรวจการมี cookie ก่อน ส่วนลายเซ็นและสิทธิ์อยู่ใน helper/route
- 401 กับ 403: ยังไม่ผ่านการยืนยันตัวตน กับไม่มีสิทธิ์ตาม policy

ข้อจำกัดที่ควรทราบ: HttpOnly ป้องกัน JavaScript อ่าน cookie โดยตรง ไม่ใช่คำยืนยันว่าป้องกันช่องโหว่ทุกชนิดแล้ว

### จุด 2: การตรวจช่วงเวลาจองทับซ้อน

ต้นทาง: [booking POST](../../app/api/booking/route.ts) บรรทัด 152

```ts
const conflictingBooking = await prisma.booking.findFirst({
  where: {
    vehicleId,
    status: { in: ["PENDING", "APPROVED", "CHANGED", "IN_PROGRESS"] },
    startDate: { lte: end },
    endDate: { gte: start }
  }
})
```

บทพูด:

> จุดนี้ค้นหารายการของรถคันเดียวกันที่ยังเกี่ยวข้องกับการจอง โดยดูว่าเวลาเริ่มเดิมไม่เกินเวลาจบใหม่ และเวลาจบเดิมไม่น้อยกว่าเวลาเริ่มใหม่ ถ้าพบแปลว่าช่วงเวลาชนกัน route ตอบ 409 ก่อนสร้างคำขอครับ หลังจากนั้นยังมี query ตรวจช่วงงานซ่อมอีกชุดด้วย

ตัวอย่างสำหรับชี้ให้เห็นเงื่อนไข:

| รายการเดิม | คำขอใหม่ | ผลตามโค้ด |
|---|---|---|
| 09:00–12:00 | 10:00–11:00 | ทับซ้อน |
| 09:00–12:00 | 12:00–13:00 | ทับซ้อน เพราะเปรียบเทียบแบบรวมขอบ |
| 09:00–12:00 | 13:00–14:00 | ไม่ทับรายการนี้ แต่ยังต้องตรวจรายการอื่น/งานซ่อม |

คำถามต่อยอด: “ถ้ากดจองพร้อมกันสองคน ป้องกันได้แน่นอนหรือยัง?”

> ปัจจุบันเป็นการตรวจระดับ application และ schema ยังไม่มีข้อบังคับกันช่วงเวลาทับซ้อนโดยตรง จึงยังต้องเสริมการควบคุมการแข่งขัน เช่น transaction isolation หรือ constraint ที่เหมาะสม พร้อมทดสอบ concurrent requests ครับ

อย่าตอบว่า composite index กันเวลาทับซ้อนให้แล้ว index `[vehicleId, startDate, endDate]` ช่วยค้นหาแต่ไม่ได้บังคับกฎนั้น

### จุด 3: การรับ–คืนรถและบันทึกการใช้จริง

ต้นทาง: [pickup](../../app/api/booking/pickup/route.ts) บรรทัด 63

```ts
const updatedBooking = await prisma.booking.update({
  where: { id: bookingId },
  data: {
    status: "IN_PROGRESS",
    mileageStart,
    pickedUpAt: new Date()
  },
  include: {
    user: { select: { name: true, email: true } },
    vehicle: { include: { type: true } }
  }
})
```

บทพูด:

> ก่อนถึงจุด update มีการตรวจว่าเป็นเจ้าของรายการ สถานะเป็น APPROVED หรือ CHANGED และเลขไมล์เริ่มไม่น้อยกว่าปัจจุบันครับ จากนั้นบันทึกสถานะกำลังใช้งาน เลขไมล์เริ่ม และเวลารับจริง อีกคำสั่งจึงเปลี่ยน Vehicle เป็น IN_USE ส่วนตอนคืนต้องตรวจว่าอยู่ระหว่างใช้และเลขไมล์คืนไม่ต่ำกว่าเริ่ม จึงบันทึก COMPLETED กับ returnedAt ครับ

จุดที่เปิดตอบเพิ่ม: [return](../../app/api/booking/return/route.ts) บรรทัด 55, 63 และ 116

- Booking.status เป็นวงจรหนึ่งรายการ ส่วน Vehicle.status เป็นสถานะรถปัจจุบัน
- คืนรถแล้วอาจมีงานซ่อมหรือรายการใช้งานอื่น จึงต้องพิจารณาสถานะรถต่อ
- เวลาจอง `startDate/endDate` แยกจาก `pickedUpAt/returnedAt`
- ใน user pickup/return ที่ตรวจรอบนี้ คำสั่งเปลี่ยน Booking กับ Vehicle ยังแยกกัน ไม่ได้อยู่ใน `$transaction` เดียวกัน จึงห้ามอธิบายว่าสำเร็จร่วมกันแบบ atomic แล้วทั้งหมด

### จุด 4: ระยะทางที่รายงานใช้

ต้นทาง: [getDistance](../../lib/vehicle-usage-analysis/calculate.ts) บรรทัด 77

```ts
function getDistance(booking: BookingRow) {
  if (
    booking.mileageStart === null ||
    booking.mileageEnd === null ||
    booking.mileageEnd < booking.mileageStart
  ) {
    return null
  }
  return booking.mileageEnd - booking.mileageStart
}
```

บทพูด:

> รายงานหาระยะทางจากเลขไมล์สิ้นสุดลบเริ่มของแต่ละเที่ยวครับ ถ้าขาดค่า หรือเลขไมล์ย้อนกลับ จะคืน null เพื่อบอกว่าคำนวณไม่ได้ aggregate จะรวมเฉพาะระยะทางที่ใช้ได้และนับ validMileageTrips แยกไว้ รายงานจึงบอกความครบถ้วนของข้อมูลด้วย ส่วน AI รับตัวเลขที่ระบบคำนวณแล้วไปสรุปครับ

ตัวอย่าง: 3 เที่ยว ระยะทางใช้ได้ 50 และ 80 กม. อีกเที่ยวไม่มีเลขไมล์ จะได้จำนวน 3 เที่ยว ระยะทางรวม 130 กม. เฉลี่ย 65 กม./เที่ยวที่เลขไมล์ใช้ได้ ความครบถ้วนเลขไมล์ 66.7% ทั้งหมดเป็นตัวอย่างสมมติสำหรับอธิบายสูตร

อย่าพูดว่า null คือ 0 หรือใช้ currentMileage ปัจจุบันแทนระยะทางรายเดือน

คำตอบที่ควรใช้:

ต้องเปิดเผยว่าชื่อผู้ใช้และทะเบียนรถอยู่ในข้อมูลที่ส่งให้ provider แม้ไม่ได้ส่ง email, token, password และข้อความการเดินทางดิบ การตรวจ schema/key/ข้อความบางรูปแบบยังไม่ใช่การรับประกันความถูกต้องของทุกข้อสรุป

## 5. คำถามหลัก 12 ข้อ พร้อมแนวตอบสั้น

### 1. ทำโครงการนี้เพื่อแก้ปัญหาอะไร?

“เพื่อจัดการคำขอใช้รถและติดตามประวัติให้เชื่อมกันครับ ผู้ใช้ค้นหารถตามช่วงเวลา ผู้อนุมัติพิจารณาคำขอ และผู้ดูแลติดตามงานซ่อมกับรายงานได้” ต่อด้วยที่มาปัญหาที่มีหลักฐานในเล่ม อย่าแต่งว่าหน่วยงานเดิมใช้กระดาษหรือ Excel หากยังไม่มีข้อมูลนั้น

### 2. ทำไมเลือก Next.js, Prisma และ PostgreSQL?

“Next.js รวมหน้าเว็บกับ API ไว้ในโครงการเดียว Prisma ช่วยเขียน query และ relation ด้วย TypeScript ส่วน PostgreSQL รองรับข้อมูลที่มีความสัมพันธ์ เช่นผู้ใช้ รถ และรายการจองครับ” ถ้าเหตุผลที่เลือกจริงต่างจากนี้ให้เล่าตามที่ทำ อย่าอ้างว่าเร็วที่สุดโดยไม่มีผลเปรียบเทียบ

### 3. กดจองแล้วข้อมูลผ่านอะไรบ้าง?

“ฟอร์มเปลี่ยน state แล้ว submit ส่ง POST เข้า API ตรวจตัวตน สิทธิ์ ข้อมูล และเวลาชนกัน จากนั้น Prisma สร้าง Booking เป็น PENDING และส่งผลกลับให้ UI อัปเดตครับ”

### 4. ทำไมต้องแยก Role กับ Permission?

“Role ระบุกลุ่มผู้ใช้ Permission ระบุงานที่อนุญาต route สามารถกำหนดทั้งสองเงื่อนไขร่วมกัน จึงปรับสิทธิ์ของบทบาทได้โดยไม่พึ่งการซ่อนปุ่มครับ”

### 5. มีทั้งหมดกี่ตาราง และ Booking สำคัญอย่างไร?

“schema มี 8 models ครับ Booking เชื่อมผู้ขอ รถ และผู้อนุมัติ พร้อมวันเวลาและเลขไมล์ของแต่ละเที่ยว ส่วน User กับ Vehicle จึงมีความสัมพันธ์ผ่านรายการจองที่มีข้อมูลธุรกิจอยู่ด้วยครับ”

### 6. รถ AVAILABLE จองได้เสมอหรือไม่?

“ต้องตรวจช่วงเวลาที่ต้องการกับรายการจองและงานซ่อมด้วยครับ AVAILABLE เป็นสถานะปัจจุบัน ไม่ได้หมายความว่าว่างทุกช่วงในอนาคต”

### 7. แนะนำรถใช้ AI หรือไม่?

“ส่วนแนะนำรถใช้สูตรใน API ครับ คะแนนคือเลขไมล์ปัจจุบันบวกจำนวนงานซ่อมคูณหนึ่งหมื่น หลังกรองรถที่เข้าเงื่อนไขแล้วเรียงคะแนนต่ำก่อน ส่วน AI อีกส่วนใช้สรุปข้อมูลการใช้งานย้อนหลัง” น้ำหนักในสูตรเป็น heuristic ที่กำหนดไว้ ยังไม่มีผลยืนยันว่าเป็นสูตรทำนายรถเสีย

### 8. รู้ได้อย่างไรว่ารายงานระยะทางถูก?

“คำนวณจากเลขไมล์แต่ละเที่ยวที่เสร็จสิ้น ตรวจค่าที่ขาดหรือย้อนกลับ มี tests ของสูตร และแสดงความครบถ้วนข้อมูลครับ ระยะทางรวมเป็นผลรวมจากเที่ยวที่ตรวจเลขไมล์ได้ ไม่ควรสรุปว่าข้อมูลที่ขาดเท่ากับไม่วิ่ง”

### 9. AI ผิดได้ไหม และตรวจอย่างไร?

“ผิดได้ครับ ระบบตรวจรูปแบบและ key อ้างอิงกับหลักฐาน รวมถึงข้อจำกัดข้อความบางอย่าง แต่ยังต้องให้ผู้ดูแลอ่านประกอบข้อมูลต้นทาง การตัดสินใจยังอยู่กับผู้รับผิดชอบครับ”

### 10. ทดสอบอะไรแล้วบ้าง?

“วันที่ 31 ตุลาคม รัน npm test ผ่าน 161 tests จาก 29 ไฟล์ TypeScript และ lint ผ่านครับ ส่วน browser E2E ฐานข้อมูล บริการอีเมล/AI และ deployment จริงต้องรายงานแยกตามสิ่งที่ตรวจสำเร็จ ไม่ใช้ unit tests ยืนยันทั้งหมดครับ” เปลี่ยนส่วนท้ายเมื่อมีผล Demo จริง

### 11. ถ้าเขียนหลายตารางแล้วล้มเหลวกลางทางจะเกิดอะไรขึ้น?

“ต้องดูว่าเส้นทางนั้นครอบด้วย transaction หรือไม่ครับ user pickup/return ที่ตรวจนี้ยัง update Booking กับ Vehicle แยกกัน จึงมีความเสี่ยงข้อมูลไม่สอดคล้องหากบางขั้นล้มเหลว แนวทางต่อไปคือจัด transaction และทดสอบ failure path ตามกฎงานครับ” อย่าพูดว่าทุก route ใช้ transaction เพราะมีบาง route ใช้

### 12. ส่วนไหนที่คุณรับผิดชอบ และได้เรียนรู้อะไร?

กรอกคำตอบจากงานจริง: “ผมรับผิดชอบ [โมดูลที่ทำจริง] โดยทำ [การออกแบบ/โค้ด/ทดสอบที่ทำจริง] ปัญหาที่พบคือ [เหตุการณ์จริง] แก้ด้วย [สิ่งที่ทำจริง] และตรวจด้วย [หลักฐาน] ครับ” ถ้าทำเป็นทีมให้แยกงานตนเองจากงานเพื่อน อธิบายเครื่องมือและความช่วยเหลือที่ใช้ตามจริง ไม่ใช้สคริปต์อ้างความเป็นเจ้าของทุกส่วนโดยไม่มีหลักฐาน

อ่านคำถามต่อยอดเพิ่มเติมได้ใน [คู่มือซ้อมสอบเดิม](05-defense-practice.md)
